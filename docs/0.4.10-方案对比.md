# 0.4.10 源码对比与采纳

对比基准：本项目 `e203bba` 与用户提供的 `CacheKeeper-0.4.10-source/`。参考目录只读保留，不作为项目源码或部署产物上传。参考版本的发布或真机验证状态不能由版本号、注释和升级说明推定。

## 结论

保留当前项目作为底座，吸收参考版本的可取设计后重新实现和验证。参考版本功能入口较多，但未证明清理收益更大或设备行为更稳定。

| 比较项 | 参考 0.4.10 的实际代码 | 采纳决定 |
| --- | --- | --- |
| 基线与目录限写 | `Baseline.m` 仅凭出生时间筛选新文件；`Permissions.m` 清除属主写位 | 不采纳。新文件不等于无用，旧缓存被永久保留；父目录限写影响正常工作文件 |
| 大目录处理 | `Baseline.m` 到 1 秒/30000 条就中止，再次调用重新枚举，且中止后仍执行删除 | 保留当前可续扫机制；不将扫描截断说成多轮完整推进 |
| 数据目录保护 | 收集直接父目录，但保护集可能在截断时不完整；只检查名称 | 采纳意图。先完整检查一个目录，命中数据库/登录态后保护该目录和后代；检查失败或目录改变时不删 |
| APP Group | `Scanner.m` 读取 groupContainerURLs，却只以主 APP 状态决定共享数据删除 | 采纳只读统计与 Filza 跳转。共享容器一律不锁、不删 |
| 网络缓存开关 | `Cleaner.m` 启动时替换共享 NSURLCache，磁盘和内存容量均为零 | 采纳独立开关；保留当前实例跟踪和恢复，仅限制磁盘。新配置默认关闭，现有显式配置保持行为 |
| 人工开启 | `Prefs/ScanPage.m` 选择目录时仍自动开启 APP；未开启 APP 仍写生命周期信号 | 保留当前总开关唯一授权。选择目录、切换模式、网络选项均不启用 APP |
| 首次开启 | 列表主动开启时预选标准 Caches，无需先检测 | 采纳。首次开启预选 Caches/tmp，执行端核验真实路径；已有选择含空列表均不覆盖 |
| 设置页效率 | 按刷新周期复用配置读取 | 采纳。仅缓存展示快照，写入仍重新读取，不能用旧快照覆盖配置 |
| 降级 | 以短时退出、新文件数推断故障，再转清理 | 不采纳该推断。无法区分用户退出、其他崩溃和插件故障，不以此扩大删除 |

## 实施与验证

1. 原生回归补充独立开关迁移、只读共享目录、数据库晚出现、目录中途变化、父目录去重与人工开启隔离。
2. 独立网络开关继续保存在 appEnabled.plist 中，避免 policy.plist 引入重复状态源；自动/只禁止模式才使用此开关，只清理模式始终不限制网络。
3. 清理按目录先检查、后删除，检查与删除都分批续扫；受保护目录和未知内容保持不动，保留创建/修改/ctime 的 60 秒保护及无链接路径访问。
4. 主容器按现有父目录展示；每个共享组以 Group/<组ID>/ 前缀列出同级目录，只读标识在 UI 与执行端共同约束。
5. 复核 diff、运行 GitHub 原生回归、Theos 编译和 deb 检查，再发布测试包。真机注入、第三方私有 API 和实际空间收益单独验收。
